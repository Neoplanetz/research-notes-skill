# 연구노트 작성 규칙

노트 한 건을 쓰기 전에 이 문서 전체와 `example-note.md`를 읽는다.

## 1. 구조 (예시 노트 그대로)

```
## 1. 목적          글머리표 2~3개
## 2. 수행 내용
### 2.1 소제목      소제목 2~4개, 소제목마다 글머리표 3~6개
                    명령어 · 설정 예시 상자는 필요할 때만, 6줄 이하
                    그림은 노트 전체에서 0~2장
## 3. 결과          글머리표 2~4개
## 4. 다음 계획     글머리표 1~2개 (기간의 마지막 노트는 후속 과제)
```

- 분량 목표 1~2쪽. 4쪽은 상한이지 목표가 아니다.
- 본문에 표 금지. 굵은 글씨 · 이모지 금지.
- 글머리표는 2단계까지만.

## 2. 문장

- 모든 줄은 단답형 명사형으로 끝낸다: `구성`, `작성`, `정리`, `확인`, `확보`, `검토`, `적용`, `변경`, `분리`, `추가`, `반영`, `도출`, `개선`, `검증`
- 줄 끝에 마침표 `.`를 찍지 않는다.
- 서술형 금지: `~했다`, `~한다`, `~이다`, `~함`, `~됨`, `~하였음`
- 한 줄에 한 가지 작업. 같은 종류를 나열할 때는 쉼표나 ` · `로 짧게 잇는다.
- 원인 → 조치는 `→`로 쓴다: `AMCL 초기 위치 설정 → 시작 직후 위치 추정 안정화`
- 영어 커밋 메시지는 한국어로 옮기되, 코드 · 파일 · 명령 · 패키지 이름은 원문 그대로 쓴다.

금지 표현 (기계가 쓴 티가 나는 말):
`이로써`, `이를 통해`, `~를 좌우하는 핵심 요소`, `다음 세 가지`, `효과적으로`, `성공적으로`, `획기적`, `원활한`, `다양한`, `~에 기여`, `~을 도모`, `~할 수 있었음`

개발 과정 잡음 금지 — 노트는 연구 작업 기록이지 작업 대화 기록이 아니다:
- AI 도구 이름(Claude, Codex, GPT 등), 리뷰 라운드, "사용자 승인 · 피드백 · 게이트"
- 커밋 해시, 브랜치 이름, HEAD, PR 번호
- 버리고 안 쓴 대안과 그 이유, 내부 파라미터 값 나열

## 3. 사실

- 커밋 메시지 · README · docs에 적힌 것만 쓴다. 수치도 그 기록에 있는 것만.
- 테스트 · 시뮬레이터 · 앱 · 빌드를 직접 실행해서 확인하거나 새 수치를 만들지 않는다.
- "확인", "검증"은 기록에 그 확인 결과가 있을 때만 쓴다.
- 그림은 레포에 이미 있는 이미지(README, `docs/`, `images/` 등)나 사용자가 준 파일만 쓴다. 새 화면을 캡쳐하지 않는다.
- 캡션은 그림에 실제로 보이는 것만 쓴다. 그림을 직접 열어 보고 쓴다. (예: A200 로봇이 보이는 화면에 J100이라고 쓰지 않음)

## 4. 제목과 실험내용요약

- 제목: 명사구. 예: `표준 시뮬레이션 도커 구성 및 Clearpath J100 적용`
- 실험 제목(`[약칭] 제목 ('26, 4/10)`)은 100바이트까지(UTF-8): 한글 1자 3바이트, 영문 · 숫자 · 기호 · 공백 1바이트. 약칭과 날짜가 약 20바이트라 제목은 80바이트 이하로 쓴다(한글만이면 26자). 넘으면 `--check`가 경고.
- 제목에 날짜를 넣지 않는다(파일명과 복사용 제목에 자동으로 붙음).
- 실험내용요약: 정확히 7줄. 노트 순서(목적 → 수행 내용 → 결과)를 따라 한 줄씩 뽑는다. 한 줄 45자 안팎. 마침표 없음.

좋은 예:
```
- 관제 웹 대시보드 사용자 인증 · 권한 관리 구조 검토
- auth.py, session.py, config.yaml 기준 수정 지점 정리
- 토큰 발급 · 갱신 API 및 만료 시간 30분 적용
- 관리자 · 운영자 · 열람자 3단계 권한 정의
- 로그인 5회 실패 시 계정 잠금 규칙 적용
- 권한별 메뉴 노출 · API 접근 제한 구조 검토
- 운영 서버 적용 기준과 사용자 안내 문서화 방향 확보
```

나쁜 예:
```
- 토큰 발급 API 작성, 로그인 화면은 다크 모드 색상 수정.     ← 마침표, 서로 다른 작업 두 개를 한 줄에
- 부하 테스트 1,000명 동시 접속 성공, 응답 120 ms 확인.        ← 기록에 없이 직접 실행해서 만든 수치
```

## 5. 주제 나누기

- 노트 수 = 계획표의 `todo` 칸 수. 작업 순서대로 앞 칸부터 채운다.
- 중요한 커밋 우선: 기능 추가, 구조 변경, 검증 결과, 배포 · 등록. 오타 · 서식 · 병합 · 리뷰 반영만 한 커밋은 단독 주제로 쓰지 않는다.
- 작업이 칸보다 많으면 작은 작업을 합친다. 적으면 한 작업을 설계 · 구현 · 검증 · 배포 · 문서화 단계로 나눈다. 단, 기록에 근거가 없는 단계는 만들지 않는다.
- 근거가 정말 모자라면 억지로 채우지 않고 사용자에게 빈 칸 수를 알린다.
- 이미 쓴 노트가 다룬 주제와 다른 노트에서 쓴 내용은 다시 쓰지 않는다.
